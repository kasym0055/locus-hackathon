# Hosted Node capability decision

The selected target is Vercel Functions using the Node.js runtime. The app pins Node to `24.x`, which Vercel documents as available for builds and functions and as the default for new projects. The capability route sets `runtime = "nodejs"`, `dynamic = "force-dynamic"`, and `maxDuration = 60`.

Vercel documents a 300-second default and maximum duration on Hobby with Fluid compute, and a Standard function instance at 2 GB. Those published limits are sufficient for the route's 28-second stream, subject to the selected account's current plan and usage. Vercel's pricing material says function invocations and duration are priced/usage-tracked; the actual account plan, remaining allowance, and any overage setting must be checked after authenticated deployment.

## Capability probe

`GET /api/capability` is disabled by default. A full probe requires `CAPABILITY_PROBE_ENABLED=true`, a non-empty `CAPABILITY_PROBE_TOKEN`, and a project-owned `CAPABILITY_PROBE_ENDPOINT`; there is no request-controlled URL. It streams NDJSON frames numbered 0, 1, and 28, with client-side arrival timestamps recorded by the probe. The route builds a self-authored 5,000 × 4,000 raster, samples RSS before, during, and after native work, performs no more than two simultaneous Sharp decodes, hashes decoded output, and reports each instance's memory limit.

The probe makes one cancelled client stream request with a generated run ID and polls its token-protected cancellation status. The route owns an internal `AbortController`; both request and stream cancellation trigger it, and its timing waits and outbound HEAD fetches share the signal. Cancellation evidence is stored in the existing Upstash Redis service under the dedicated `locus:capability-probe:v1:cancellation:` prefix with the generated run ID and a 60-second TTL. The TTL removes completed records while leaving a short retry window if a status response is interrupted. Records contain only bounded probe state and timestamps, never tokens, URLs or application data. The cancellation lifecycle is registered with Next `after` so a disconnect does not abandon the Redis write. Missing Redis configuration makes the cancellation probe fail closed; production never falls back to process memory. Full runs require six actually-dispatched successful outbound requests, measured active-request counts, and a maximum of two requests to the configured origin. A reported host memory limit is mandatory before the script can report a 25% headroom pass. `--allow-unknown-memory` permits the deployed mechanics check to return `inconclusive`, never `pass`, when the platform reports `0` for the limit.

The original deployed probe used a module-level `Map`. A same-instance regression proved that stream cancellation fired and cleanup reached a completed record, while an otherwise identical status request evaluated in a fresh module instance could not see that record. This matched the production timeout because the cancelled stream and status poll are independent serverless requests with no instance-affinity guarantee. The shared Redis record removes that cross-request process-memory dependency without weakening the cleanup requirement.

Run the production probe only after setting `DEPLOYMENT_URL` and `CAPABILITY_PROBE_TOKEN` in the execution environment:

```powershell
pnpm probe:host -- --url $env:DEPLOYMENT_URL
```

The script first cancels a request after the streamed start frame, obtains its server cancellation status, then makes three concurrent requests. It requires an early first client arrival, a distinct final arrival after 27 seconds, the 20-megapixel source and two-decode ceiling, configured outbound attempts/successes/concurrency, and per-instance memory headroom of at least 25%.

Local exercise on 2026-09-16: the revised script recorded client first arrivals of 58/137/262 ms and final arrivals of 28,049/28,125/28,221 ms; the server cancellation record confirmed request-abort cleanup and outbound abort; and it observed 600,117,248 bytes peak RSS. Local Node reported a constrained-memory limit of `0` for every instance, so the explicit `--allow-unknown-memory` mode returned `inconclusive`. This verifies route mechanics locally only; it is not host-capability evidence.

## Task 2 publisher transport validation — 2026-09-16

Publisher retrieval now uses Undici with all DNS answers screened by parsed address ranges, an explicitly pinned numeric socket destination, the original Host/TLS server name, and TLS certificate verification enabled. Redirects are followed manually only after a fresh destination and access check, up to three redirects. Each invocation combines caller cancellation with at most three seconds of remaining request time. All publisher/robots/image requests share a process-wide ceiling of six outbound requests and two per hostname; crawl pacing can make that ceiling lower. Per-run publisher attempts (including redirects) stop at eight, image attempts at 24, and origin policy checks at eight.

Streaming wire and decoded-body guards cap HTML at 2,000,000 bytes, raster inputs at 5,000,000 bytes, and robots at 512,000 bytes. Only one supported content coding is accepted. Undici `request` has no automatic redirect interceptor. Its [documented request/dispatcher APIs](https://undici.nodejs.org/) and the installed connector implementation were checked for socket pinning and TLS behavior.

`CRAWLER_CONTACT_URL` must contain an operator-confirmed real project/contact HTTPS URL. Missing or placeholder contact configuration disables crawling. No real contact URL was invented or configured in this task. The default source policy remains `transient_only` and `link_only`; public availability or a citation does not establish permission. Trusted server composition may supply documented origin-specific publisher permissions to candidate extraction, and must retain stricter discovery restrictions and attribution obligations. Publisher terms prohibitions can be supplied through the fetcher's server-only construction options; these options are not request-controlled and no proxy route was added.

Deterministic tests use self-authored synthetic HTML and a local socket fixture. The fixture maps only the transport's already-validated destination to a local test server; production has no destination-validation bypass. Tests cover forbidden IP ranges, mixed DNS, rebinding, redirect validation, byte/timeout/cancellation cleanup, robots and publisher restrictions, Retry-After, crawl pacing, and independent retention/display decisions. These tests prove local mechanics, not a live publisher's permissions or hosted execution.

The deployed native/network check was attempted again with `pnpm probe:host`. It stopped before any network request with `DEPLOYMENT_URL/--url and CAPABILITY_PROBE_TOKEN are required`. The authenticated deployment blocker above remains open. ## Task 5 stream and browser wiring — 2026-09-16

The production `POST /api/session` and `POST /api/profile` routes use the Node runtime, force dynamic execution and a 60-second host maximum. The application request budget is 27 seconds from receipt, including origin/session/body checks and admission. Ordinary query bodies are bounded to 2 KiB before parsing; selection tokens remain rejected until Task 6. Responses use versioned, sequence-checked NDJSON with no-store/no-transform/nosniff headers. One writer owns sequence numbers and terminal closure. Request and stream cancellation abort the shared work signal and release the admission lease.

Set `APP_ORIGIN` to the exact deployed origin and `SESSION_SECRET` to an operator-generated secret of at least 32 characters. Sessions have random 256-bit IDs with an expiring HMAC signature in an HttpOnly, Secure, SameSite=Lax cookie. Existing valid sessions are reused. No secret is sent to the browser. The current production IP adapter supports only Vercel (`VERCEL=1`) and its overwritten single `x-forwarded-for` address; it rejects missing/multiple addresses and HMACs the result. It does not trust arbitrary forwarding headers on unsupported hosts. This follows Vercel's [documented request-header behavior](https://vercel.com/docs/headers/request-headers), checked on 2026-09-16. Generic self-hosting needs a verified server-side peer adapter; setting `TRUSTED_PROXY_IP` alone cannot establish a trusted peer inside a standard Next Request.

`PUBLISHER_POLICIES_JSON` is optional, server-only configuration: a maximum 16 KiB JSON array of at most 16 strict `UsagePolicy` objects, each scoped to one exact HTTPS origin and carrying at least one non-empty documented operator basis. Expired policies do not grant anything. This is not a source whitelist or an identity/evidence bypass. The default remains link-only; missing display permission produces an honest missing photo. A direct publisher discovery may use its documented grant; Brave-derived restrictions remain binding. Access/robots checks, identity resolution, caption association, location support, safe media preparation and AI assessment still run separately. M1 only admits one verified campus card; no complete profile or generated campus description is claimed.

The browser uses direct `<img>` delivery with no referrer, never `next/image` or a local media proxy. It has explicit Cancel/Retry controls, discards state on a new search and aborts on unmount. Failed delivery removes the image and reports it unavailable. No local/session storage or persistent image/search cache is used.

Local validation: all unit/integration tests pass except the existing eight real-Redis tests, which remain explicitly service-gated. The fixture E2E runtime lives only under `tests/`: it uses the actual application UI, route handler, resolver, discovery planner, safe-fetch, Sharp preparation, OpenAI SDK, decision and coordinator. Only external transport/media/model responses and the unavailable admission-store interface are authored fixtures. The ledger boundary does not emulate Redis Lua or prove distributed accounting. Three browser cases pass: actually loaded image/source/score/partial final; remote image failure; Cancel and explicit Retry with empty local/session storage. This is fixture verification, not live M1 acceptance.

Task 5 review correction: a publisher-page grant does not license a different image host. Discovery now intersects the page policy with a separate exact image-origin grant. Safe-fetch preserves its observed redirect destinations only in request-local metadata; preparation checks the original image URL, every redirect destination and the final URL against current documented grants before model processing or remote delivery. This also blocks an unpermitted intermediate host that redirects back to the publisher. The emitted URL is the inspected final image URL, and restrictive policy/attribution obligations from all involved image origins survive into the card. Missing, expired or disallowed grants cannot produce a remote card. Future changes by an external host after this request remain outside the control of direct browser delivery.

Caption verification now requires an explicit named-campus construction rather than co-occurring institution/city/category words. Visitor, partner, joint, negated and otherwise ambiguous captions are withheld even when the model says supported. M1 intentionally favors false negatives for prose outside these narrow attribution forms. The model receives a separate bounded selected-university comparison object (name, campus, city and country, each at most 200 characters); it is not publisher evidence and cannot establish ownership or award confidence. Deterministic source/permission/location gates still decide verification.

The profile route registers its request/runner lifetime synchronously with [Next `after(promise)`](https://nextjs.org/docs/app/api-reference/functions/after), before admission. Its required injectable `waitUntil` hook is used only to make this host boundary testable; production passes `after` directly. A terminal NDJSON record does not close the response: EOF waits for the runner's lease release. Request/stream cancellation still aborts the 27-second pipeline immediately, while the registered lifetime keeps cleanup tracked after disconnect. Release is attempted once with a three-second cleanup guard, independent of the aborted work signal; the real Upstash transport retains its existing two-second timeout with no retries. This cleanup allowance does not authorize new pipeline work or extend its 27-second deadline and remains inside the configured 60-second host duration. Release failure rejects the tracked lifetime for host reporting and errors an open stream instead of claiming successful EOF or appending another terminal. Delayed-release and stalled-cancellation tests verify these mechanics locally; hosted lifecycle/Redis execution still requires the blocked live validation.
